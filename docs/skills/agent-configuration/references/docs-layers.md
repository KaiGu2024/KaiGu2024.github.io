# Research repository structure and documentation layers

Read when scaffolding or auditing a research project's layout, analysis naming, or notes wiki.

### Directory roles

Use this layout by default for new research projects. Create only directories the work needs. For existing projects, document their actual layout and preserve established paths unless migration is requested. AGENTS.md supplies the operational guidance governing these directories.

| Layer | Holds | Rule |
|---|---|---|
| `code/` | Authoritative ingestion, preparation, analysis, presentation, and packaging code | Keep executable sources here; express execution order through the pipeline entrypoint |
| `data/` | Raw, intermediate, and analysis-ready datasets plus computational caches | **Never edit `raw/` — read only**; classify by role, not file size |
| `writing/` | Editable manuscript, slide, report, and promotion sources and their supporting assets | Keep authored sources here and rendered deliverables in `output/` |
| `output/` | Figures, tables, slides, reports, papers, and promotion deliverables | Preserve retained outputs and trace them to their generating inputs and sources |
| `replication/` | An assembled release containing the dependencies needed to reproduce the declared results | Export from authoritative sources; verify independently of the working repository |
| `docs/` | Stable reference specs | Change only when design/schema/method changes |
| `notes/` | The living wiki | Changes every session |

```text
project/
├── README.md
├── AGENTS.md
├── code/
│   ├── ingestion/
│   ├── preparation/
│   ├── analysis/
│   ├── presentation/
│   └── packaging/
├── data/
│   ├── raw/
│   ├── intermediate/
│   ├── analysis/
│   └── cache/
├── writing/
├── output/
│   ├── figures/
│   ├── tables/
│   ├── slides/
│   ├── reports/
│   ├── paper/
│   └── promotion/
├── replication/
│   ├── README.md
│   ├── code/
│   ├── data/
│   ├── environment/
│   ├── manifest.json
│   ├── run_all.*
│   └── output/
├── docs/
└── notes/
```

`run_all.*` denotes a driver in the project's language, not a literal filename. The release's `output/` contains results generated by that package. Include publication sources and supporting assets in the release when rebuilding documents is part of its declared scope.

Classify files by their role: an analysis input belongs in `data/analysis/` even when small; a reader-facing regression table belongs in `output/tables/` even when stored as CSV. Put figure/table generation scripts in `code/presentation/`, editable `.tex`, `.qmd`, or equivalent publication sources in `writing/`, and rendered PDFs/HTML in the corresponding `output/` subdirectory. Self-contained authored deliverables may also be their own editable sources; document that role and preserve them.

**Location does not establish disposability.** Retained data, release snapshots, and final outputs remain protected, as do authoritative files in legacy locations such as `output/paper/ms/`, `output/code/`, or `output/data/`. Keep disposable build files in a separately identified build root and apply the [source-protection procedure](source-protection.md); neither `output`, `temp`, nor `build` in a path authorizes deletion. Adopting this layout does not authorize moving or deleting existing files.

### Analysis naming and outputs

Use a stable substantive result-family name (for example, `localization`) consistently across `code/analysis/localization/`, `output/figures/localization/`, `output/tables/localization/`, notes, and documentation. Preserve established numbering when present. Alternative research designs, specifications, estimators, and presentation designs stay within that family in each applicable directory. Create a new family only for a different substantive result, not for another attempt or run.

Use descriptive filenames to distinguish metrics and variants, such as `employment_baseline.pdf`, `employment_alternative_controls.pdf`, and `wages_baseline.pdf` within `output/figures/localization/`. Use meaningful variant names rather than revision labels such as `v2` or `final_final`.

Keep run dates, run identifiers, and manifests in provenance records using the project's existing provenance location, or a family-local `provenance/` directory if none exists. Record input versions or hashes, the specification, code revision and any uncommitted changes, environment, and output paths or hashes so each retained result can be traced to its generating run. A rerun adds provenance; it does not create a dated or numbered copy of the result-family folder.

Git preserves revisions of committed, tracked files through the `version-control` skill. Do not duplicate result folders to simulate version history. For artifacts outside Git, provenance must identify their retained storage location and version; a manifest alone does not preserve artifact contents. Honor existing retention requirements when updating outputs.

Keep input preparation, estimation, and presentation code in the corresponding `code/` subdirectories. Each result-generating script should consume a named input, record its provenance, and write predictable outputs keyed to the result family, metric, and variant. Store reusable computational intermediates, including cached estimates, in `data/cache/` with their generating code, input versions, and parameters recorded. A cache is not automatically disposable, and redrawing a figure from cached coefficients does not reproduce the estimation.

### Replication releases

Treat `replication/` as an assembled release, with authoritative development files remaining in `code/`, `data/`, and `writing/`. Use a packaging script or equivalent build target to select and copy the required files. Fix originals and rebuild; do not hand-maintain divergent exported copies. Preserve retained release versions according to the project's retention policy.

Define the package's starting point and outputs explicitly:

- **Fast reproduction:** starts from identified analysis-ready data or documented cached artifacts. State which construction or estimation steps are skipped.
- **Full reconstruction:** starts from documented source data and runs preparation, estimation, and presentation. Include data-construction code even when source data cannot be redistributed, and document how authorized users can obtain those inputs.

Both modes can use separate targets in one package. The subset must include every dependency needed for the declared scope: shared functions, configuration, lookup tables, and supporting assets as well as analysis scripts. Exclude unrelated experiments, not necessary upstream steps merely because they are expensive. Check the target journal's current requirements before treating a fast-reproduction package as submission-ready.

Include a README with data origins, availability/access conditions, a data dictionary or link, execution order, software requirements, expected runtime/hardware, and a script-to-exhibit map. Include dependency/version specifications and a manifest recording the source commit, any uncommitted source state, input versions or hashes, selected files and hashes, and expected output paths. A release should identify the exact source state used; a commit hash alone does not describe uncommitted changes. Document omitted restricted data and verification limits.

Verify a real exported copy outside the working repository using its documented entrypoint and environment. It must not rely on parent-project paths such as `../code/`, personal absolute paths, or undeclared local caches. Compare regenerated results with the retained targets using appropriate numerical tolerances or artifact checks; report which modes actually ran and any unavailable inputs. Do not claim full reconstruction from a fast-path check.

### Data formats and storage

Prefer Parquet for tabular analysis data when the project's tools support it; preserve variable meanings, types, missing-value conventions, and codebooks. Use JSON for small manifests, configurations, and structured metadata rather than as the default format for large rectangular datasets. Preserve source formats in `data/raw/`; conversion belongs in the preparation pipeline. Choose interoperable alternatives when the replication environment requires them.

Disk compression does not guarantee low memory use. Read only needed columns and rows and use batch or lazy processing where appropriate. Record retained large-data locations and versions when storage is external to Git; smaller exported inputs must still preserve the observations and variables needed for the declared analyses.

### Basis for this convention

This layout is the adopted research-project default, not a universal journal requirement. [Cookiecutter Data Science](https://cookiecutter-data-science.drivendata.org/#directory-structure) separates raw/intermediate/processed data, executable sources, and generated reports. [Good Enough Practices in Scientific Computing](https://pmc.ncbi.nlm.nih.gov/articles/PMC5480810/) supports separation and explicit processing steps but also permits processed data within results. The [DIME Handbook](https://worldbank.github.io/dime-data-handbook/publication.html) distinguishes data publication, reproducibility packages, and written products.

The [AEA policy](https://www.aeaweb.org/journals/data/data-code-policy) requires raw-to-analysis transformation code even when raw data cannot be shared; the [Social Science Data Editors README template](https://social-science-data-editors.github.io/template_README/template-README.html) guides package documentation. [Parquet](https://parquet.apache.org/docs/overview/) and [Arrow dataset documentation](https://arrow.apache.org/docs/python/dataset.html) explain columnar storage, selective reads, and batch processing. These sources informed the convention adopted on 2026-11-03; verify current submission requirements when preparing a release.

### Documentation roles

| Role | Kind | Audience | Changes | Answers |
|---|---|---|---|---|
| `AGENTS.md` | Front door | The **agent** | When durable decisions / layout / constraints / conventions change | "How do I *operate* in this repo?" |
| `README.md` (root) | Front door | **Humans** | When onboarding facts change | "What *is* this and how do I start?" |
| `docs/` | Content — **stable reference** | Human + agent | Only when the design / schema / method actually changes | "What *exactly* is X?" |
| `notes/` | Content — **living wiki** | Agent (+ human) | Every session | "What do we *think* / what's next?" |

Keep AGENTS.md and README brief and link into the content directories. Environment and build configuration hold setup details; `docs/methodology/` holds method explanations.

- **`docs/`:** Use neutral, declarative prose. Organize stable material into `design/` (experiment/design specifications frozen before analysis), `methodology/` (replicator detail), `technical/` (data, code, and analysis architecture), and `references/` (external immutable material). Visualization and table conventions belong to their dedicated skills.
- **`notes/`:** Use Markdown, YAML frontmatter, and Obsidian `[[wiki-links]]` for evolving arguments and commentary. The core pages are `index.md` (catalog; search first), `overview.md` (evolving thesis and open work), `log.md` (chronology), and `methodology/decisions.md` (choices and rationale). Subfolders can include immutable `sources/`, `concepts/`, `entities/`, `findings/`, `literature/`, `methodology/`, and `paper/`. Link each fact from one authoritative page instead of copying it elsewhere; favor cross-links over hierarchy.

### History and wiki maintenance

- **Without a wiki:** README holds orientation, detailed rationale, and a dated update log.
- **With a wiki:** Move chronology to `notes/log.md`, rationale to `notes/methodology/decisions.md`, and the evolving thesis to `notes/overview.md`. README holds orientation; maintain one running log.

Include the maintenance, typed logging, and periodic wiki-lint rules from the [AGENTS.md template](../SKILL.md#generating-a-research-agentsmd-workflow) in persistent project instructions. Keep detailed wiki procedures in `notes/index.md`.
